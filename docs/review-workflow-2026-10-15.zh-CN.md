# 文章流程、多平台视频与 Kubernetes 复核

本次检查以已运行的 `20261015-workflow-v8` 为基线。保留此前未提交改动；不改文章／视频 ID、旧目录、objectKey、V1 hash、历史审批与原始文件，不新增依赖或数据库迁移。

## 已修复的边界

1. **回退版本来源**：回退原来读取可被 `configure` 覆盖的目标镜像，升级准备失败时可能启动未经采用的版本。现在从私有 runtime marker 读取实际采用的四个镜像；停止和切换编排时保留这组镜像，直到新的门控采用开始。保存配置与调用的 Kubernetes／Docker context 不符时，在操作资源前拒绝执行。
2. **旧媒体预览**：稳定媒体引用没有文件扩展名，原界面可能将 MP4 当图片，或不显示注册素材。改为对受控媒体 URL 发 HEAD 查询 MIME，查询缓存独立于编辑缓冲。ID 与文件仍保持原值，不为预览复制媒体。
3. **未保存任务输入**：新建按钮和任务链接曾先清空本地 seed，再触发导航保护，选择“继续编辑”也可能丢输入。移除 seed；新建／选中状态统一由 URL 管理，导航获准后才重建表单。异步加载既有任务时显示加载状态，不先挂载空白新建表单。
4. **视频审阅边界**：共享脚本仍有未保存修改时，平台交付审批按钮禁用并提示先保存、复核成片。平台文案仍可独立维护，目标审批、版本和物理成片绑定不变；目标成片选择只列当前内容修订，旧成片继续在历史区可见。
5. **并发冲突**：Supabase 的 CAS／租约冲突原来被统一成普通请求错误，HTTP 层无法返回 409。只识别受控冲突状态／SQL 消息模式，映射为通用修订冲突；不把 SQL details、路径或凭证传给 UI。
6. **批量失败定位**：同名账号的结果原来只显示账号名，且无法直接定位对应平台版本。结果现在标明平台并携带文章 ID／平台参数；只影响页面定位，分发任务仍逐篇逐账号独立保存。

## 架构与兼容结论

- 保持模块化单体：浏览器查询／契约、应用用例、持久化和运行部署职责分开。过渡期浏览器仅复用明确列出的纯业务 schema；Node 执行、文件和数据库模块由边界测试禁止进入浏览器。
- 文章事务提交／不可变修订／回执／后续任务复用既有 Supabase RPC；文件是可恢复导出，不参与 UI 路由设计。本轮无需批量回填旧记录。
- 视频 V1 算法保持原值；V2 继续独立绑定目标文案、账号、所选 MP4 及 YouTube 设置。一个目标变化不撤销另一个目标审批；未知提交仍先核对，不能自动重发。
- Compose／K8s 使用同一业务和文件权威，回退只切应用编排。Supabase、pgmq 和 pg_cron 保持原部署；禁止两套应用同时写同一工作区。
