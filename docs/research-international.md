# International publishing integration research

Research date: 2026-10-10 (Asia/Singapore). Primary platform documentation, vendor documentation, and upstream repositories were inspected. No platform account, OAuth grant, paid subscription, or real publication was verified by this research subtask. Prices and permissions must be checked again in the actual account before activation.

## Recommendation for the two stages

Build the first stage around a small product-owned content and delivery ledger, with Postiz behind a replaceable outbound API adapter and authenticated Chrome publishing handoffs for unsupported or unapproved channels. Store durable product data in Supabase if a database is needed. Codex can generate and adapt content, prepare assets, execute the local workflow, and operate the selected Chrome profile. The application must retain its own content, publication intent, attempts, receipts, and account capability records, so its operation is understandable after a Codex turn ends.

Postiz is the strongest maintained general publishing component examined: its latest release is v2.25.0, published October 2, 2026, with active platform error handling and upload fixes. It already separates queued work from provider execution. Using its API lowers custom adapter maintenance. Self-hosting still requires each platform's developer credentials and approval; hosted Postiz supplies its own integrations according to its documentation. Neither path grants permissions that the platform or connected account does not possess. [Postiz releases](https://github.com/gitroomhq/postiz-app/releases), [self-host configuration](https://docs.postiz.com/self-host/configuration/reference)

Complete stage one before starting a standalone SaaS runtime. Its acceptance criterion should be one real end-to-end content run: source evidence → generated platform variants → assets → connected account → publication attempt → actual platform URL or an explicit blocked/manual state. A scheduling API response, account signup, or filled browser form is insufficient. The second stage can then replace Codex orchestration with a durable server worker and licensed model APIs, preserve the Supabase ledger, and retain API/native capabilities separately. Browser-only integrations still need a user-controlled browser agent or an approved server integration.

## Exact Postiz REST contract for implementation

Cloud base URL: `https://api.postiz.com/public/v1`. API keys use `Authorization: <api-key>` directly, without a `Bearer` prefix. The official bundled Docker deployment exposes the app at `http://localhost:4007`; its public route is normally reached through `/api/public/v1`. Configure the base URL and probe `/integrations` against the actual deployment rather than deriving it from the frontend hostname. Public controller prefix is `/public/v1`; reverse-proxy routing affects the external path. Create-post rate limit is currently 100/hour in cloud and default 90/hour self-hosted, configurable with `API_LIMIT`. [API introduction](https://docs.postiz.com/public-api/introduction), [controller source](https://raw.githubusercontent.com/gitroomhq/postiz-app/main/apps/backend/src/public-api/routes/v1/public.integrations.controller.ts)

`GET /integrations` returns a top-level array. Each channel has `id`, `name`, `identifier`, nullable `picture`, `disabled`, nullable `profile`, and optional `customer: {id,name}`. Use these real IDs. The provider field is `identifier` here; nested channel records in the posts listing use `providerIdentifier`. [Integration API](https://docs.postiz.com/public-api/integrations/list)

Verified minimal scheduling request to `POST /posts`:

```json
{
  "type": "schedule",
  "date": "2026-10-11T09:00:00.000Z",
  "shortLink": false,
  "tags": [],
  "posts": [{
    "integration": { "id": "ACTUAL_CONNECTED_CHANNEL_ID" },
    "value": [{ "content": "Approved channel-specific content", "image": [] }],
    "settings": { "__type": "x", "who_can_reply_post": "everyone" }
  }]
}
```

The ID and content above illustrate the schema, not ready-to-submit data. `type` can be `now`, `schedule`, or `draft`; the current DTO requires a valid ISO date even where the immediate-post behavior ignores it. `shortLink`, `tags`, the nonempty `posts` array, and each post's nonempty `value`/media array must follow the validated shape. Provider settings differ. Upload media first using `POST /upload`, multipart field `file`; reference the resulting `{id,path}` in `image`. An HTTP 200 create response is an array:

```json
[{ "postId": "CREATED_POST_ID", "integration": "CONNECTED_CHANNEL_ID" }]
```

This is a creation/scheduling receipt. It is not proof of platform publication. [Create API](https://docs.postiz.com/public-api/posts/create), [create DTO source](https://raw.githubusercontent.com/gitroomhq/postiz-app/main/libraries/nestjs-libraries/src/dtos/posts/create.post.dto.ts)

`GET /posts?startDate=<UTC ISO8601>&endDate=<UTC ISO8601>` returns `{posts: [...]}`. Each row includes `id`, `content`, `publishDate`, `releaseURL`, `state`, `error`, `settings`, and `integration: {id,providerIdentifier,name,picture}`. The current implementation additionally returns fields such as `releaseId`, grouping, creation method, tags, and recurrence interval. Handle nullable release URL/error. Source states are exactly `QUEUE`, `PUBLISHED`, `ERROR`, `DRAFT`. The docs show settings as an object, while current repository/schema return nullable serialized JSON text; tolerate an object, JSON string, or null at the adapter boundary. [List API](https://docs.postiz.com/public-api/posts/list), [repository query](https://raw.githubusercontent.com/gitroomhq/postiz-app/main/libraries/nestjs-libraries/src/database/prisma/posts/posts.repository.ts), [Prisma schema](https://raw.githubusercontent.com/gitroomhq/postiz-app/main/libraries/nestjs-libraries/src/database/prisma/schema.prisma)

No general idempotency key/header guarantee was found in the public contract or controller. The create implementation generates a fresh batch UUID and creates each channel separately. Recent duplicate protection covers republishing supplied existing post IDs; it does not make an identical new HTTP request safe to retry. A multichannel request can therefore be ambiguous after a partial failure. [Creation implementation](https://raw.githubusercontent.com/gitroomhq/postiz-app/main/libraries/nestjs-libraries/src/database/prisma/posts/posts.service.ts)

Recommended adapter behavior (design inference): persist the channel-specific content hash, assets, schedule, and attempt before the call; make one channel request per attempt; persist returned post ID immediately; reconcile via `GET /posts` by ID and time range. After timeout, mark the attempt uncertain and inspect likely candidates before retrying. Do not automatically republish when no unique match exists. Treat `PUBLISHED` plus the platform release URL and its verified visibility as final success; distinguish TikTok inbox handoffs or pending moderation from public publication. Keep errors and reconnect actions visible.

## AiToEarn integration details and independence limits

Its documented browser extension SDK supports `xhs`, `wxSph`, and `douyin`. An operator can choose authorization-only installation, allowlist the application origin, and use `window.AIToEarnPlugin` without signing into the AiToEarn website. `getVersion` and `checkPermission` identify readiness. `login(platform)` reads the platform account already authenticated in the same Chrome browser; it does not perform sign-in automatically. Its raw account result can include `loginCookie`: never log it, render it, sync it to Supabase, or transmit it through the product. Only map nonsecret account identifiers and display metadata. [Extension publishing SDK](https://docs.aitoearn.ai/zh/use/plugin-publish)

The extension's `publish` method accepts the platform, image/video type, title/description, files or fetchable media URLs, cover, topics, and visibility, plus a progress callback. A result includes success/failure information and work/share identifiers where available. Xiaohongshu supports images/videos, Channels uses video, and Douyin supports both. This is a browser-session integration and still requires platform login, valid session, and any challenge/final confirmation. Its documentation does not establish official platform authorization for cookie-based publishing. It is a stage-one candidate requiring live validation; it cannot by itself supply a server-only stage-two SaaS.

Hosted v2 publishing flow endpoint: `POST https://aitoearn.cn/api/v2/channels/publish/flows` for China-issued keys, or international host `https://aitoearn.ai/api` with the corresponding international key; header `X-Api-Key`. Body structure is `content` (title/body/media URL/cover), required `publishAt`, `items` (platform, real accountId, platform option, optional per-account overrides), optional external `flowId`, and optional context. Bilibili options include a required category identifier. Query the platform capability/option schema instead of hardcoding all providers. [Create publishing flow](https://docs.aitoearn.ai/api-reference/post-api-v2-channels-publish-flows)

HTTP 200 is insufficient: require business `code === 0`, then track returned `data.flowId` and task records. Those records carry status, platform work ID/link, link resolution errors, and publish errors. Douyin can enter status `8`, waiting for the user's mobile confirmation. An external flowId is not documented as a deduplication guarantee. The current docs advertise 1,000 free publishing requests/month, with extra X provider costs, but overage guidance conflicts between an August guide and September endpoint documentation. Check account pricing before adopting the relay. [Publishing flow guide](https://docs.aitoearn.ai/zh/use/publish-flow)

## Concrete stage-one validation checklist

1. Verify the application repository and baseline before implementation; do not modify an unrelated financial-data MCP checkout.
2. Record Chrome profile `radarxai@gmail.com`, Supabase preference, chosen adapter, required OAuth scopes, and actual account capabilities in project documentation.
3. Generate platform-specific variants with source links and asset manifests; record explicit review/approval state and AI/commercial disclosures where required.
4. Connect one viable international account and publish a real test. Verify the resulting platform URL, visibility, and ledger state. Then add platforms incrementally.
5. For each native channel, prepare a complete publish package and hand off to the real authenticated creator page in Chrome. Record the resulting URL or exact unmet login/phone/QR/developer-review step.
6. Exercise an ambiguous timeout and a failed authorization state; ensure no blind duplicate publication and that reconnect instructions persist.
7. Demonstrate restarting the local workflow without losing content, pending attempts, account blockers, or receipts. Only then undertake server runtime migration.

The first-stage evidence should distinguish implementation, local smoke tests, account setup, OAuth approval, queued jobs, and real publication. The report does not claim any of those operational steps have already occurred.
